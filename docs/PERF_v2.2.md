# 果冻三消 v2.2.0-mobile · 手机性能优化报告

日期：2026-10-10（UTC+8）。基线：v2.1.0-octoAB。目标：手机上流畅，同时保持 v2.1 的画面（包括八爪鱼 B）。

> **重要说明**：以下所有数字都来自无头 Chrome + SwiftShader（软件 GL）+ CDP CPU 降速（4x / 6x），
> 只能**近似**模拟手机，不能代替真机测试。GPU 填充率、真机 GPU 驱动、发热降频都**没有被测到**。
> 在这个环境里，绘制主要由 CPU 软件光栅化完成，所以帧时间偏悲观，而且主要受画布合成/光栅成本影响。
> 截图、像素对比和自动化测试通过，不等于已经验证真机手感或真机性能。

## 1. 测试方法
- Playwright（playwright-core + 系统 Chrome，`--use-gl=angle --use-angle=swiftshader`），视口 390×844，DPR 3，isMobile + hasTouch。
- CDP `Emulation.setCPUThrottlingRate` 设为 4x 和 6x。
- 场景：idle（静止）、cascade（连锁下落）、combo（特殊组合大爆炸）、octoB（`?octo=B` 下持续操作）。
- 指标：rAF 帧间隔 avg / p95 / p99，>16.7 ms 和 >33 ms 帧占比，游戏内 sim / draw 分项（`window.__PR` 钩子），JS 堆，GL draw call / 顶点数，2D 绘制操作数。
- 脚本：`test/prof_v22.js`、`test/run_prof_v22.sh`；原始数据 `work22/prof_results.jsonl`。
- v2.1 测了两次（基线 + 复测），用来体现环境本身的噪声（约 10–20%）。

### 绘制量（不降速）
- GL：idle 1 次 draw call / 7.6k 索引；octoB 17–19 次 draw call，索引 high 52k / medium 19k / low 13.6k。
- 2D 每帧操作数（v2.1 → v2.2 high）：idle 37 → 35（medium 18、low 9）；cascade 116 → 69；combo 270 → 98。
- JS 堆峰值：11–21 MB → 8–17 MB。

**结论**：在同样环境下，high 档（默认画质）帧时间约为 v2.1 的 40–55%；静止时从约 55–65 ms 降到约 24 ms。
连锁 / 大爆炸期间 high 档仍明显超过 16.7 ms，所以自动分档会降到 medium / low。

## 3. 自动分档的落点
- 起始档：high；若 `hardwareConcurrency ≤ 4` 或 `deviceMemory ≤ 3`，从 medium 起步。
- 规则：2 秒为一个窗口；连续 2 个窗口平均 > 20 ms 则降一档；平均 ≤ 18 ms 且 JS ≤ 8 ms，持续 upWait（5 秒起、每次翻倍、最多 60 秒）且距上次降档 ≥ 8 秒才升一档；切换后 1.5 秒内不判定；> 250 ms 的异常帧忽略。
- 演示录像（4x，自动）：high → medium（3.8 s）→ low（9.5 s），之后稳定在 low，约 30 fps（录像本身也占 CPU）。6x：4.0 s → medium，9.7 s → low。日志：`work22/tier_settle.jsonl`。
- 在无头环境里静止时停在 medium、游玩时停在 low，这是软件光栅造成的；真机有 GPU，很可能能停在 high 或 medium，需要真机确认。
- `test/tier_v22.js`：人为加 30 ms 负载 8 秒 → 降到 low；去掉负载后逐级升回 high。通过。

## 4. 改了什么
1. **画布分层**：原来整屏 2D 画布任何变化都要重绘/重新合成。现在分为：背景+顶栏+HUD（cA，只重绘脏区域，用单个包围矩形裁剪）、棋盘底板（cBoard，震屏用 CSS translate）、连消光晕（cGlow，1/4 分辨率，用 CSS 透明度/缩放动画）、WebGL 果冻层、2D 特效层（cB，空时跳过，只清包围盒）。这是收益最大的一项（cascade 4x 104 → 56 ms）。
2. **WebGL 批处理**：持久 VBO/IBO（bufferSubData），对象池复用批次，光照 uniform 每帧只设一次；地面汁渍改为烘焙进图集、在 GL 里一次画完。
3. **DPR 上限**：GL 层最高 2，按档降到 1.75 / 1.5；2D 文字层保持 3（low 为 2）。
4. **物理**：保持 1/120 固定步长；只有 low 档用 1/60。已验证弹性一致：周期 317 ms 和静止时间与 1/120 相同，落地峰值高约 6%（`work22/timestep_v2.2.txt`）。曾试过 maxLag 0.05，在 20 fps 抖动下出现慢动作（sim/real 0.87），已放弃。
5. **休眠与零分配**：姿态插值写入复用对象，休眠姿态复制而不是引用；飞出的果冻在 medium/low 用刚体模式。
6. **粒子**：对象池 + 每档上限；水滴/火花用预渲染精灵，火花色相量化到 36 级以便缓存。
7. **HUD**：只在内容签名变化时重绘；连消横幅/夸奖文字缓存成精灵。
8. **音频**：沿用节点池；页面隐藏时挂起 AudioContext。
9. **资源**：果冻贴图和八爪鱼材质 256px（预乘 alpha + Lanczos），图标 ≤ 192px，PNG 无损压缩。下载量 4511 KB → 1957 KB（gzip 3773 → 1629 KB）；图集显存约 11 MB → 2.8 MB。脚本 `tools/make_mobile_assets.py`。
10. **后台暂停**：页面隐藏时浏览器停止 rAF、游戏挂起音频；返回时重置计时，不会“追帧”。

## 7. 局限
- 无头 SwiftShader + CPU 降速只是近似，**没有测 GPU 填充率**；真机可能更快（有 GPU）也可能因发热降频更慢。
- high 档与 v2.1 有轻微差异：GL DPR 2、256px 贴图、精灵粒子和汁渍、光晕用 CSS 实现（没有内圈填充）。
- 内存分配速率比 v2.1 高（v2.1 1.5–2.9 MB/s，v2.2 2–7 MB/s，octoB high 7.0 MB/s），可能来自每帧的签名/transform 字符串和体积对象；堆峰值反而更低，但可能引起 GC 小卡顿，下一步可继续优化。
- 手机省电模式会把 rAF 限制在 30 Hz（约 33 ms/帧），自动分档会认为“太慢”而降到 low；这时画面略简化但不影响玩法。
- 自动分档只看帧时间，不看电量/温度。
- low 档 1/60 物理与 1/120 弹性基本一致，但落地峰值约高 6%。

## 8. 如何在手机上试
- 最简单：把 zip 解压后用电脑起一个本地服务器（如 `python3 -m http.server 8000`），手机和电脑连同一 Wi-Fi，用手机浏览器打开 `http://<电脑局域网IP>:8000/index.html?dev=1`，看左下角的档位和 fps。
- 可以对比 `?q=high`、`?q=medium`、`?q=low` 的手感和流畅度，以及 `?octo=B`。
- 如需要，我可以帮你临时托管一个测试链接（例如 Vercel 预览）——**目前没有部署任何东西**，需要你确认后才会做。
